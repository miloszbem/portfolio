# SEO & Server Config Fixes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Usunąć błędy i ostrzeżenia wykryte przez Google Rich Results Test i Seobility (2026-07-28), podnosząc Server configuration z 0% i Page quality z 65%.

**Architecture:** Poprawki w trzech warstwach: (1) Cloudflare Worker - nagłówki HTTP odpowiedzi dla assetów, (2) komponenty Astro + copy PL/EN - treść i struktura nagłówków, (3) konfiguracja Cloudflare (dashboard, poza repo) - redirecty HTTP→HTTPS. Zadania decyzyjne wymagające danych od użytkownika są wydzielone i **nie mogą** być rozwiązane przez zgadywanie wartości.

**Tech Stack:** Astro 7 (static output), Cloudflare Workers (`worker/index.ts` + Workers Assets), TypeScript, JSON-LD schema.org.

## Global Constraints

- Wcięcia: taby. Cudzysłowy: pojedyncze.
- Zero em-dash (—) i en-dash (–) w treści. Tylko zwykły myślnik `-`.
- Nie dodawać funkcji, refaktorów ani abstrakcji poza zakresem zadania.
- Komentarze tylko tam, gdzie logika nie jest oczywista. Bez JSDoc.
- Każde zadanie kończy się `git commit`. **Bez `git push`** - push tylko na wyraźne polecenie użytkownika.
- Po każdej zmianie w `src/` lub `worker/`: `npx astro build` musi przejść bez błędów.
- Nie fabrykować danych kontaktowych/adresowych w schema. Brak danych = pytanie do użytkownika, nie wymyślona wartość.

## Ustalenia z rekonesansu (zweryfikowane, nie zakładane)

Wykonano przed napisaniem planu, wyniki wiążące dla zadań:

| Sprawdzenie | Komenda | Wynik |
|---|---|---|
| Charset w nagłówku HTTP | `curl -sI https://miloszbembnowicz.pl/` | `content-type: text/html` - **brak `charset=utf-8`**, potwierdzone |

### Task 1: Charset UTF-8 w nagłówku HTTP odpowiedzi

**Model:** Haiku 4.5 - mechaniczna zmiana, kompletny kod w briefie, jeden plik.

**Files:**
- Modify: `worker/index.ts:92`

**Interfaces:**
- Consumes: `env.ASSETS.fetch(request)` (istniejący binding, `Env` w `worker/index.ts:5-10`)
- Produces: brak nowych symboli eksportowanych. Zmiana jest lokalna dla handlera `fetch`.

**Dlaczego nie `public/_headers`:** plik `_headers` używa wzorca `/*`, który objąłby też CSS/JS/PNG i nadpisał ich `Content-Type` na `text/html`, psując stronę. Filtrowanie po typie odpowiedzi w Workerze jest precyzyjne i bezpieczne.

- [ ] **Step 1: Sprawdź stan przed zmianą (baseline)**

```bash
curl -sI https://miloszbembnowicz.pl/ | grep -i '^content-type'
```

Oczekiwane: `content-type: text/html` (bez `charset`). To potwierdza, że problem istnieje.

- [ ] **Step 2: Podmień return na wersję z charset**

W `worker/index.ts` zamień linię 92:

```ts
		return env.ASSETS.fetch(request)
```

na:

```ts
		const assetResponse = await env.ASSETS.fetch(request)
		const contentType = assetResponse.headers.get('Content-Type')
		if (!contentType?.startsWith('text/html') || contentType.includes('charset')) {
			return assetResponse
		}

		const headers = new Headers(assetResponse.headers)
		headers.set('Content-Type', 'text/html; charset=utf-8')
		return new Response(assetResponse.body, {
			status: assetResponse.status,
			statusText: assetResponse.statusText,
			headers,
		})
```

- [ ] **Step 3: Zweryfikuj, że Worker się kompiluje**

```bash
npx --yes esbuild worker/index.ts --bundle --outfile=/dev/null --format=esm
```

Oczekiwane: `Done in Xms`, zero błędów.

- [ ] **Step 4: Zweryfikuj, że build strony przechodzi**

```bash
npx astro build
```

Oczekiwane: `[build] Complete!`

- [ ] **Step 5: Commit**

```bash
git add worker/index.ts
git commit -m "fix(worker): add charset=utf-8 to HTML response Content-Type"
```

- [ ] **Step 6: Weryfikacja po deployu (dopiero gdy użytkownik wypushuje)**

```bash
curl -sI https://miloszbembnowicz.pl/ | grep -i '^content-type'
```

Oczekiwane po deployu: `content-type: text/html; charset=utf-8`
Jeśli nadal bez charset: sprawdź, czy Cloudflare nie serwuje z cache (`CF-Cache-Status: HIT`) - wtedy purge cache lub poczekaj.

- [ ] **Step 3: Przedstaw użytkownikowi instrukcję do wyklikania**

Poproś użytkownika o wykonanie w panelu Cloudflare (dash.cloudflare.com → domena `miloszbembnowicz.pl`):

- Opcja A (zalecana): zostaw bez www. Zero pracy, zero ryzyka. Ktoś, kto wpisze `www.`, dostanie błąd DNS.
- Opcja B: dodaj w Cloudflare rekord CNAME `www` → `miloszbembnowicz.pl` (proxied) + Redirect Rule 301 z `www.*` na apex. Łapie ruch od osób wpisujących `www`, kosztem jednej reguły do utrzymania.

Zapisz wybór użytkownika w tym pliku planu przed przejściem dalej.

### Task 6: Opcjonalne pola schema - decyzja użytkownika

**Model:** Opus 5 - dotyczy danych osobowych/firmowych i ryzyka fabrykacji. Wymaga rozmowy, nie edycji.

- Produces: `personSchema` - obiekt serializowany do JSON-LD w `Layout.astro:57`. Dodanie pól nie zmienia sygnatury, tylko zawartość.

**Twarda zasada:** Google Rich Results Test zgłasza brak `telephone`, `priceRange` i `address` jako **opcjonalne**. Użytkownik powiedział wcześniej, że nie ma zarejestrowanej działalności, więc nie ma adresu firmowego. **Nie wolno** wpisać zmyślonego adresu, NIP-u, telefonu ani zakresu cen "żeby test świecił na zielono". Fałszywe dane w schema to ryzyko dla użytkownika, nie kosmetyka.

- [ ] **Step 1: Zapytaj użytkownika o każde pole osobno**

- `priceRange` - schema.org przyjmuje tu zapis typu `1000-5000 PLN` albo symbolikę `$$`. Mamy publiczne ceny od 1 000 zł, więc to pole da się wypełnić prawdziwymi danymi. Zapytaj, jaki górny zakres podać (albo czy użyć samego `od 1000 PLN`).

```bash
python3 -c "
import re
src = open('src/i18n/copy.ts', encoding='utf-8').read()

print('tylko EN:', en - pl)
"
```

Oczekiwane: oba zbiory puste. Niesymetryczne klucze to błąd typów, który ujawni się dopiero w runtime dla wersji EN.
